Flash-Flags v1.1.9 - Source Precedence, Input Screening & Documentation Accuracy
=================================================================================

Release Date: 2026-09-20
Type: Bug fix / behavioural change

FIXED
-----
- Configuration source precedence was inverted between config files and
  environment variables. A value found in a JSON config file marked the flag as
  "changed", which caused LoadEnvironmentVariables to skip it, so the config
  file silently won over the environment -- the opposite of the documented
  contract.

  Each flag now records which source supplied its value (default < config < env
  < cli) instead of a single boolean. A source writes a flag only when it ranks
  at least as high as the one that currently owns the value, which makes the
  ordering independent of the order the loaders run in. Calling LoadConfig or
  LoadEnvironmentVariables manually after Parse can no longer downgrade a
  command-line value either.

  The rule has a single definition, Flag.canSet, and is enforced inside both
  write paths -- setFlagValueFrom for parsed strings and setFlagValueFromConfig
  for typed JSON values -- rather than by their callers, so a loader added later
  cannot reintroduce the inversion by forgetting to check. The loaders still
  test the same predicate first, purely to skip work on a value that would be
  discarded. A write from a lower-priority source is discarded and reported as
  success: being outranked is the normal outcome of layered configuration, not
  a failure. Such a value is neither parsed nor validated, so a leftover
  environment variable cannot fail a parse whose result it would never reach.
  The comparison is >= rather than >, so a repeated command-line flag still
  keeps its last value.

- Duration flags could not be loaded from a configuration file: any config
  containing a duration key failed Parse with "unsupported flag type: duration".
  JSON has no duration type, so both encodings are now accepted -- the string
  form understood by time.ParseDuration ("30s", "1m30s") and a plain number of
  nanoseconds, which is what encoding/json emits for a time.Duration.

- The example modules under examples/ and stdlib/ did not build after the v1.1.8
  toolchain bump: their go directive still said 1.23 while the parent module
  required 1.25.9. All module go directives are now aligned at 1.25.9.

CHANGED
-------
- Input screening no longer tries to infer intent from a value's contents.

  It previously rejected any value containing "/etc/", "/proc/", "/sys/",
  "rm -rf", "drop table", "$(", a backtick, the %n %s %x %d %c %p format verbs,
  "../" or "..\\", or matching a Windows device name. That denylist stopped no
  attack: "a; rm -rf ~", "deploy && restart", "cat f | grep x" and
  "..%2f..%2fetc" all passed it untouched, because ';', '|', '&&' and percent
  encoding were not on the list. Meanwhile it rejected ordinary input --
  "--config /etc/myapp.conf", a --command argument holding "rm -rf /tmp/build",
  a --template of "%s-%d.log", and the string "Comp Ltd", which matched the
  "COM" device prefix.

  What remains is input hygiene, which does not depend on where a value is
  headed: the 10000-byte length cap, null bytes, and C0 control characters other
  than tab, newline and carriage return. The fast path is unchanged.

  If you relied on the removed checks as a security control, they were not one.
  Screen values at the point of use, where their meaning is known: run os/exec
  without a shell, parameterize SQL, resolve and confine paths before opening.

- The configuration file path allowlist has been removed.

  loadConfigFromFile previously rejected any path containing ".." and any
  absolute path outside five prefixes (/tmp/, /opt/, /etc/, /var/tmp/,
  /var/folders/, plus Windows equivalents). The path never comes from parsed
  input -- SetConfigFile and AddConfigPath are called by the application, and
  LoadConfig runs before parseArguments -- so the allowlist filtered a value
  that was never hostile, while causing real breakage:

    * A config under the user's home directory was rejected. That is the
      location AddConfigPath's own documentation uses as its example, and one of
      the three default auto-discovery paths.
    * A directory merely named "v1..2" was rejected by the ".." substring check.
    * /tmp and /var/tmp were allowed. They are the world-writable prefixes on
      the list, and therefore the only ones where planting a symlink before
      startup is worth anything -- which worked, and still does.

  The check is now that the target is a regular file. This closes a denial of
  service the allowlist permitted: a FIFO under /tmp passed it, and os.ReadFile
  on a FIFO blocks until a writer appears, hanging Parse indefinitely. Reading a
  character device such as /dev/zero is refused for the same reason. os.Stat
  answers both without opening anything.

  This is a robustness check, not a security boundary: it is racy against a
  concurrent replacement of the path, and symlinks are still followed. An
  application deriving the config path from untrusted input must validate and
  confine it before calling SetConfigFile.

- Configuration auto-discovery advertised default search directories it never
  used. AddConfigPath's documentation, and the API reference, stated that with
  no paths added discovery searches ".", "./config" and $HOME. LoadConfig
  returns early when neither a config file nor a path is set, and findConfigFile
  returns at the top when a config file is set, so the default list was
  unreachable in both directions -- the coverage profile showed the branch at
  zero hits against the full suite.

  The dead branch has been removed and the documentation corrected, rather than
  the defaults implemented. Implementing them would mean a program that never
  opted into configuration files silently loading ./<name>.json whenever one
  happened to sit in the working directory, which changes flag values from
  outside the program's control.

  Removing it also cleared the one gosec finding on the package: G703 (CWE-22,
  path traversal via taint analysis) flagged os.Stat on a path joined from
  os.Getenv("HOME"), which existed only in that unreachable branch. The PR
  workflow runs gosec without "|| true", so that gate now passes.

  Documented alongside it: AddConfigPath does not expand its argument, so
  "$HOME/.myapp" looks for a directory literally named "$HOME". The examples in
  doc.go and the API reference used that form and could never have matched; they
  now resolve the home directory with os.UserHomeDir, which is also the portable
  call, since HOME is normally unset on Windows.

ADDED
-----
- Flag.Source() and FlagSet.Source(name) report which configuration layer
  supplied a flag's current value: "cli", "env", "config" or "default". Because
  sources are resolved by precedence, the result names the highest-priority
  source that set the flag, not the last one consulted.

DOCUMENTATION
-------------
- Removed the "lock-free" claim from the package documentation, README and API
  reference. The package contains no mutexes and no atomic operations; the real
  guarantee is that reads are safe once Parse has returned, because nothing
  mutates the flag set afterwards. Reset and ResetFlag are mutating calls and
  racing them against a read is a data race, which the race detector reports.
  The Thread Safety sections now state this explicitly.

- Corrected the description of input screening. The previous text claimed
  protection against "shell metacharacters" and command injection in general.
  The implementation is a fixed denylist: it does not filter ; | && or newline,
  URL-encoded traversal sequences, absolute paths outside three prefixes, or the
  %v, %+v, %#v, %q, %T and %[n]s format verbs. It also rejects legitimate values
  such as /etc/myapp/config.yaml. The documentation now lists exactly what is
  checked and states that this is a blunt input filter, not a security boundary.

- Documented that SetConfigFile does not resolve symlinks, so an allowlisted
  world-writable directory such as /tmp offers no protection against a symlink
  planted before startup.

- The fuzz suite asserted the removed denylist as an invariant: an accepted
  value was required not to contain "/etc/", "rm -rf", "%s" and friends. That
  encoded the antipattern as a test, making "--config /etc/myapp.conf" a
  security failure while "a; rm -rf ~" passed clean. It now asserts what the
  parser actually promises: accepted values carry no null byte or control
  character, and a value arrives exactly as it was supplied.

- All validator examples now use the comma-ok form of the type assertion. A bare
  val.(int) panics on mismatch and the panic propagates out of Parse; the
  SetValidator documentation now says so.

- Corrected stale Go version (1.23) and version number (v1.1.5) references
  across doc.go, README.md and API-REFERENCE.md.

COMPATIBILITY
-------------
No exported API was removed or changed. Both behavioural changes above are
strictly more permissive for flag values and config paths, with two exceptions
that only reject what could not work anyway: a config path pointing at a
directory, a FIFO or a device is now refused instead of failing later or
hanging. Changed() keeps its exact previous semantics
("the flag no longer holds its default value") and is now derived from the
recorded source.

Applications that unknowingly relied on a config file overriding an environment
variable will see the environment take effect instead. That is the documented
and intended behavior; FlagSet.Source can be used to audit where each value
comes from.
